### Decisive independent real-Mongo counterexample

`_commit_item()` in `monitoring.py` performs a conditional atomic **write on the lease state row** and renews the lease (`:732-777`). `_apply_result()` then writes findings/history/audit in separate documents/collections (`:1172+`). That gate is not a transaction with those later writes. Using a fresh local real MongoDB 7.0.43, I wrapped the real `_commit_item`: after it successfully committed, advanced an injected test clock by six seconds for a five-second TTL, then made worker B successfully `_claim()` a higher fence before returning to worker A. A eventually raises `MonitorLeaseLost`, but the persisted result is **1 stale finding, 1 transition, 1 `file.integrity.finding.opened` AuditEvent**; required result is 0/0/0. This is a deliberate independent counterexample: 1 collected / 0 passed / 1 failed, not included in the green suite. The temporary review-only test was removed; implementation checkout is clean.

The code and HANDOFF expressly acknowledge this residual full-TTL window. Extending the TTL reduces probability but cannot satisfy the unconditional canonical guarantee. MongoDB single-document atomicity cannot make the finding and audit writes conditional on a different claim document. A strict solution appears to require an approved architecture (for example replica-set multi-document transactions, or a redesigned co-located atomic state with its size/indexing/recovery tradeoffs), or Krum explicitly changing the guarantee. Codex cannot choose the deployment topology, storage model or security exception on Krum's behalf. **No C04 dispatch is authorized or sent.**

### Reproducible remaining defect — TOCTOU after lease verification

`_check_one()` awaits `_verify_lease()` at `backend/app/files/monitoring.py:1092`, which performs a read-only `find_one` of the state row (`:671-699`). It then calls `_apply_result → _observe` without an atomic claim condition. For a new finding, `_observe` does `find_one({id})` and `insert_one(row)` (`:1153-1201`) with only a copied numeric fence in the new row. The `_fenced` filter on existing finding updates compares only to the finding's previous fence, not to the live lease row; `_transition` likewise cannot undo the earlier insert. There is no unique `id` index on this collection. Therefore a takeover **after** `_verify_lease` but **before** the first finding insert allows the stale worker to commit a finding under its obsolete fence. Subsequent `_checkpoint` rejection is too late.

Independent deterministic real-Mongo counterexample on fresh local MongoDB 7.0.43: wrap `_verify_lease` so it first calls the real implementation, then expires worker A's claim and makes worker B successfully `_claim()` the same tenant before returning to A. A missing original makes A continue into `_observe`. Assertion that no stale finding exists fails with `assert 1 == 0`; A eventually raises `MonitorLeaseLost`, but only after its stale finding has been persisted. This is a deliberate counterexample test, **1 collected / 0 passed / 1 failed**, not a green gate. The temporary review-only test file was deleted; implementation checkout is clean. The shipped C02 real-Mongo test takes over *during the provider call*, before `_verify_lease`, so it cannot cover this later interleaving.

Required bounded correction: ensure the live claim/fence condition and finding/history/audit side effects cannot split across this takeover boundary; prove the above post-verification interleaving (including no stale finding, transition or AuditEvent) on disposable real Mongo. Preserve C02 proof and scoped projection fixes. Prevent duplicate deterministic finding identity under concurrent inserts. Do not treat another pre-write read-only lease check as an atomic fence.

### Bounded defects

1. **Stale worker can publish findings and AuditEvents after losing the claim.** `backend/app/files/monitoring.py` renews before `_integrity.check()` but does not revalidate/fence the lease after that awaited provider call. `_check_one → _apply_result → _observe/_try_resolve → _transition` mutates `file_integrity_findings` and appends AuditEvents without a holder/fence condition. Only the subsequent `_checkpoint` is fenced. Interleaving: worker A waits in a provider check; its lease expires; B claims a higher fence and resumes; A returns and opens/resolves a finding and appends an event before `_checkpoint` raises `MonitorLeaseLost`. Existing stale-worker tests exercise `_renew`, `_checkpoint`, `_finish_run`, `_release` directly, not this post-provider path. This violates the exact contract's “a stale worker cannot commit after a newer owner takes over” and can overwrite B's newer evidence/lifecycle. Add an interleaving regression including real-Mongo where appropriate and fence the finding/audit side effects, not merely the cursor.
2. **Type-specific resolution accepts incomplete evidence.** `resolution_proof()` accepts `method=server_checksum` for `permission_failure` although the provider adapter may obtain that from `stat()` without an authorized `read()`. It also resolves `provider_unavailable` on `ok` with `method=none` (adapter `verify()` can return `available` when neither a provider checksum nor readable bytes exist), and resolves `checksum_mismatch` when the canonical expected size is known but `observed.size_bytes` is missing. Independent direct calls against the exact head returned `(True, 'authorized_content_read_succeeded')`, `(True, 'provider_verification_succeeded')`, and `(True, 'canonical_checksum_and_size_match')` for those three incomplete proofs. The W0-06C contract explicitly requires actual read verification after permission denial, full provider verification after outage, and canonical checksum **and size** before closing mismatch. Keep these findings open with precise blocked reasons until evidence exists; add negative/positive tests.
3. **The alarm projection does not apply project/module scope.** `list_findings()` calls `_authorize(..., monitor.read)` without scope/module and `_may_read_file()` checks only sensitivity. The permission service's `_evaluate_one` evaluates a module restriction only when a requested module is supplied; therefore a company-scoped, module-restricted `monitor.read` assignment can list findings for other modules. Project-scoped assignments cannot request their project through this API. The contract requires any read projection to enforce tenant/project/module/sensitivity scope. Add scoped, fail-closed projection behavior and negative tests for cross-project and cross-module affected-record exposure, preserving tenant/sensitivity denial.
