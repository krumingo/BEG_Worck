## Finding 1 — new financial record can name two different people

`backend/app/master_data/legacy_adapter.py:340-355` checks for a mismatch only when both `from_person` and `from_user` resolve. If the supplied legacy `user_id` exists but is not mapped to Master, `from_user` is `None`; a separate valid `person_id` is accepted. `backend/app/routes/hr.py:231-293` then writes the legacy employee as recipient (`user_id`, `recipient_name`) and the unrelated canonical `master_person_id` on the same new advance. The employee and canonical person are not proven to be the same identity.

This is independently reproducible on the exact head with the committed synthetic fixture: after migration, `u2` remains pending; submit `{"type":"Advance","user_id":"u2","person_id":<u1 canonical ID>,"amount":10}` in enforce mode. The route returns **201**, persisting `user_id=u2` and `master_person_id=<u1 canonical ID>`. Likewise a Loan with `guest_name="Different Guest"` plus that `person_id` returns **201** and stores a display recipient inconsistent with the canonical person. The focused tests cover a mismatch only when *both* IDs are already mapped, so they miss this case. This contradicts the canonical §4.5 requirement that the new financial obligation belongs to an official, confirmed Master Person; it can misattribute a debt. Fail closed for unverified or contradictory recipient identity; add negative regressions proving no advance/payment write and an auditable denial. Do not invent a new matching rule.

### Finding — `/prices` can join another tenant's invoice and expose its data

`backend/app/routes/reports.py:53-61` first matches `invoice_lines.org_id` to the caller, then `$lookup`s `invoices` on `invoice_id == id` **without `org_id` in the join**. `reports.py:75-88` projects the joined invoice's number, issue date and `supplier_counterparty_id` into the response. C02 added tenant filters only to subsequent **name lookups** (`reports.py:119-143`); those cannot undo the earlier foreign invoice join. The resulting row is returned by `/prices` in off, shadow and enforce modes. In enforce, `annotate_refs` may label the foreign supplier ID as `unmigrated`, but that does not remove the foreign invoice data.

Independent real-Mongo reproduction on the disposable loopback server: insert one `invoice_lines` row with `org_id=tenant-A, invoice_id=shared-id` and one `invoices` row with `org_id=tenant-B, id=shared-id, invoice_no=B-SECRET, supplier_counterparty_id=foreign-supplier`. Run the route's `$match` → `$lookup` → `$unwind` → `$project` pipeline. Actual output was `[{line_id: line-a, invoice_no: B-SECRET, supplier_id: foreign-supplier}]`. The probe database was dropped immediately afterward. This is a tenant-isolation leak, not merely a missing cosmetic annotation. It also contradicts the C02 assignment's tenant-safe adapter coverage for explicitly listed `/prices`. Existing C02 report tests cover a foreign counterparty lookup, but not two invoices sharing an ID across tenants.

The remaining bounded technical correction must scope that join by the server-resolved tenant and add a real or equivalent deterministic duplicate-ID cross-tenant regression on the `/prices` response, proving no foreign invoice fields or Master reference can be returned. Inspect other identity-bearing joins within the assigned report paths, without expanding to unrelated routes. No new business rule is needed.
