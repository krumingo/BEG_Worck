### Blocking correctness defect — registered `/invoice-lines` route

`backend/server.py:138-139` registers `backend/app/routes/invoice_lines.py` as an HTTP route. `backend/app/db/__init__.py:16` binds its raw `db` to one `DB_NAME`, not a request-specific tenant database. In `invoice_lines.py`:

- `enrich_line_with_names()` at lines 158-184 resolves buyer, project, warehouse, person and company by bare `id`. The tenant-scoped list/detail routes call it at lines 230 and 439. With a B document first under the same ID, an A invoice-line response can contain B's name/code.
- `recalculate_invoice_totals()` at lines 138-156 looks up and updates the invoice by bare `id`, despite receiving `org_id`. After an A line mutation, a colliding B invoice can be selected and its financial totals changed.
- `update_invoice_line()` first proves an A line with `{"id": line_id, "org_id": user["org_id"]}` at line 457, but writes via `update_one({"id": line_id}, ...)` at line 495 and reads the result by bare ID at line 508. A B line inserted first under that ID can be modified or returned instead. The allocate path repeats this pattern at lines 553-567.

These are active code paths, not a theoretical count or a fabricated production exploit. They directly contradict the required bidirectional A/B financial isolation. The exact-head A2B collision test does not exercise `/invoice-lines`; the static guard intentionally excludes this module from its protected read set.
