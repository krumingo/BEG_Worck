## Кратък извод

Пакетът е силен диагностичен експеримент и основните бизнес дефекти са реални. Той обаче още не е самодостатъчен, безопасен и напълно възпроизводим тестов пакет и не е Implementation Gate PASS.

Данните доказват девет провалени проверки върху main, повторени по 165 пъти. Те са приблизително пет до шест първопричини, а не девет независими дефекта. Най-силно доказани са:

- анулирана фактура, която остава материален разход и input VAT;
- платен транш без finance_payments;
- паралелни трудови схеми, които допускат двойни часове и различни P&L/payroll резултати;
- аванс без idempotency защита.

## 4. Ограничения и дефекти на harness-а

### 4.1 Пускане B не е възпроизводимо от Git

README признава, че #75 е пуснат с модифицирано копие на process_bot.py, останало само в сесията. pr75_process.jsonl доказва наблюдавания резултат, но точният изпълнен тестов код липсва.

### 4.2 Липсват суровите main логове

За main са committed grouped CSV и summary, но не и raw process.jsonl, frontend/backend/db logs. Така може да се провери агрегатът и първият пример, но не всеки от 165-те случая.

### 4.3 REPORT_main.html има rendering дефект

В harness/analyze.py функцията _grouped() вече връща готова HTML таблица, а резултатът се подава повторно на table(). Главната таблица се изписва символ по символ вместо като нормална таблица.

### 4.4 Няма пълен runbook

Липсват точните команди и версии за:

- MongoDB replica set;
- Python и Node зависимости;
- frontend build;
- bootstrap на фирма, admin и subscription;
- стартиране и спиране на watcher/backend/bots/analyzer;
- проверка, че базата е празна;
- архивиране и checksum на резултатите.

Скриптовете са твърдо вързани към /tmp/claude-0, порт 27021 и конкретни demo имена.

### 4.5 Складът не се seed-ва

В seed.py създаването на warehouse и items е изключено чрез „0 and post(...)“, а process_bot.py използва предварително зададени UUID. Затова F5 не може да се възпроизведе върху действително празна база.

### 4.6 Няма fail-closed защита за средата

Ботовете изпълняват финансови POST/DELETE операции и UI ботът може да натиска анулиране/сторно. Localhost не е достатъчна гаранция. Преди първия consequential write harness-ът трябва да отказва, освен ако едновременно са изпълнени:

- database name започва с разрешен disposable prefix;
- отделен TEST_RUN_TOKEN съвпада в bot и backend;
- production hostname/credentials отсъстват;
- базата има уникален run marker;
- потребителят и tenant-ът са синтетични.

### 4.7 UI покритието е ограничено

Шест от осем роли не са работили реално. Освен това seed.py не създава users["Worker"], докато bot.js и F6 очакват такава роля. В committed pr75_process.jsonl F6 завършва с KeyError: Worker.

Затова UI изводите важат основно за Admin и SiteManager; правата на останалите роли не са пълно UI доказателство.

### 4.8 UI ботът не е детерминистичен

Осемте паралелни бота споделят една глобална random seed променлива. Асинхронното им преплитане променя реда на изборите. Всеки бот трябва да има собствен PRNG, seed и action counter.

### 4.9 FE → BE → DB корелацията е времева

- FE и BE се свързват по method/path/role в прозорец ±3 секунди;
- BE и DB се свързват по времеви прозорец до +1 секунда.

При паралелни заявки това не доказва причинност. Нужен е correlation_id, генериран за всяко действие и пренесен през frontend header, backend log, AuditEvent и domain/ledger metadata.

### 4.10 Change stream покритието е частично

watch.py следи demo_begwork, но не demo_system, и записва основно имената на променените полета, не стойностите преди/след. Следователно твърдението „следи всяка промяна в базата“ трябва да бъде ограничено до наблюдаваната tenant база и записаното metadata.

### 4.11 Неизследвани console errors

main_summary.json съдържа 1 802 console errors, докато README съобщава 0 JavaScript crashes. Двете твърдения могат да са едновременно верни, но без raw fe_errors лог не може да се оцени дали console errors са шум или функционален проблем.

## 5. Какво да се направи преди harness-ът да стане CI gate

1. Поправяне на cycle/counter документацията и HTML rendering-а.
2. Commit на точния harness за всяко пускане; никакви „копия само в сесията“.
3. Run manifest с code SHA, harness SHA, dependency lock hashes, DB names, start/end, seeds и environment flags.
4. Fail-closed disposable-environment guard.
5. Собствен deterministic seed за всяка роля.
6. Корелационен ID през UI → API → database/audit.
7. Пълен seed за Master Data и склада.
8. Поправяне на Worker акаунта и реално UI покритие за всички роли.
9. Съхранение на raw логовете или компресиран артефакт с SHA-256 и срок на пазене.
10. Повторение върху актуализиран #75, базиран върху същия main commit.
11. Превръщане на всяко потвърдено правило в малък автоматичен regression тест, вместо тричасовият бот да е единствената защита.

## 6. Решение за текущите сливания

Този пакет не е Implementation Gate PASS. Същевременно силно доказаните финансови и трудови дефекти не трябва да бъдат игнорирани заради слабостите на UI harness-а.

Препоръчано:

- засегнатите merge-и остават спрени;
- дефектите се групират по първопричина;
- всяка поправка получава кратък детерминистичен regression тест;
- след това се пуска поправеният process harness върху точния merge candidate;
- тричасовият multi-role тест остава допълнителен soak/integration слой, не заместител на CI.
