# W0-06A — deterministic legacy migration map

> Generated by `backend/scripts/w0_06a_migration_plan.py`. Do not edit by hand.
> Task W0-06A / C01, Issue #43 §8, canon FLOW-016.

A **plan**, not a migration. W0-06A moves no customer file, activates no provider
and deletes nothing. The worked examples below are produced from fixture rows in
the generator, so this document can be regenerated and diffed anywhere without
touching a tenant's data.

## 1. The shape

```text
legacy reference  ->  file_id  ->  provider location  ->  relations
```

* **legacy reference** — what the row is called today (its id, or the stored URL).
* **file_id** — derived, not drawn at random:
  `sha256(org_id | source key | legacy reference)`, truncated to the shape of a
  freshly minted id. Re-running the plan maps a row to the SAME id, so an
  interrupted migration resumes and two plans can be diffed; and the owner is
  INSIDE the hash, so the same legacy id in two tenants never produces one id.
* **provider location** — `tenants/<org>/files/<prefix>/<file_id><ext>` in the
  tenant's own provider. Derived from the identity, never the other way round:
  nothing resolves a file by its object key.
* **relations** — what the legacy row says the file belongs to.

`executable` is **0** out of 30 rows that carry content (2 rows have nothing to
migrate at all): nothing in this plan can run in W0-06A.
Two reasons hold for every row, by construction:

1. no legacy row stores a checksum, so a `REGISTER` row needs its bytes READ —
   a provider operation this task does not perform;
2. every `RELATE` / `REPLACE` row points at a file a `REGISTER` row must create
   first, and none can.

Provider onboarding (a verified Primary Storage Provider per tenant, FLOW-016
§onboarding gate) is therefore the gate on executing any of this.

## 6. Blockers that need a human answer, not more code

- `NO_OWNER` — a row with no tenant. W0-03E-A2B backfilled the legacy collections, so
  this should be empty against real data; it is still checked per row, because a
  plan that assumed the backfill was complete would migrate an ownerless file into
  whichever tenant happened to run the job.
- `UNMAPPED_CONTEXT_TYPE` — the legacy media context `message` has no collection in the active
  backend. A migration cannot invent a business record to attach those files to.
- `OPAQUE_ATTACHMENT_REFERENCE` — an attachment stored as an opaque string with no media record behind
  it. Each must resolve to a real media row or be decided on by a human; none is
  dropped.
- `INLINE_BASE64_NOT_A_FILE` — a photo stored as base64 INSIDE a database row. It has no provider
  object at all, so migrating it means WRITING bytes to a provider for the first
  time, which cannot precede provider onboarding.
- `NO_BUSINESS_RELATION` — a media row with no context. A human must say what it belongs to.
