## Преценка на оркестратора

И двете находки се приемат. Codex потвърди основното: 10 паралелни плащания → 1 победител, едно плащане на служител, авансите веднъж, платен run е заключен, изолацията между фирми работи. Остават два пропуска:

- **F-01:** атомарният запис пази само документа на Pay Run-а, а не останалите стъпки на операцията. Ако reopen или PATCH е започнал и още работи (`sync_on_reopen` / `sync_on_confirm`), mark-paid може да плати междувременно. Накрая run-ът е „платен“, а разпределенията са `reversed` или `provisional`.
- **F-02:** при грешка по средата на плащането run-ът остава `status=paid` с `paid_effects=failed`. Списъкът, UI и `paid_labor` го показват като нормално платен.

## Корекции

### F-01 — една операция на run в даден момент
- Атомарен **lock на ниво run** (например поле `op_lock: {token, op, at}`) се взема с един условен запис **преди** страничните ефекти на `mark-paid`, `reopen` и `PATCH`. Пуска се със същия token **след** като ефектите свършат (finalize/cleanup).
- Всеки конкуриращ се преход изисква да няма чужд активен lock. Иначе отказ `409` без запис.
- **Fail-closed:** ако операция падне по средата, lock-ът остава и run-ът е блокиран видимо. Без автоматично освобождаване по време в тази задача; инструментът за отключване се описва като дълг.
- Code може да предложи еквивалентен механизъм (например междинен статус), стига да покрива целия прозорец на ефектите и в двата реда на състезание.
- **Тестове на реален MongoDB с контролирано преплитане (fault-controlled), и в двата реда:**
  - mark-paid ↔ reopen;
  - mark-paid ↔ PATCH.
  - Проверява се крайното състояние на: фишове, отчети, разпределения, Outflow-и, аванси, статус и история.

### F-02 — недовършено плащане не изглежда като платено
- Плащането не трябва да изглежда завършено, докато не са минали всички ефекти. **Препоръка на оркестратора:** отделни статуси `paying` (по време на ефектите) и `payment_failed` (при грешка), като `paid` се записва само накрая. Тогава всеки потребител, който проверява `status == "paid"`, автоматично изключва недовършеното.
  - Алтернативата е `paid_effects == "done"` да се изисква навсякъде. Code избира и обосновава в PR-а.
- `_ever_paid` и заключването остават в сила и за `paying` и `payment_failed` (има `paid_at`, парите може вече да са тръгнали). Без второ плащане, без автоматичен повторен опит.
- **Списък и детайл:** връщат състоянието на ефектите. UI показва ясно „Плащането е в процес“ или „Плащането НЕ е завършено — нужна е проверка“. Минимална UI промяна (етикет/предупреждение) в `frontend/src/pages/PayRunsPage.js`, без редизайн.
- **`backend/app/services/paid_labor.py`** (`_paid_alloc_rows`) и всеки друг потребител на „платен Pay Run“, който Code намери (и проверката в payroll audit), броят само завършени плащания. Списъкът с намерените потребители се дава в PR-а.
- Fault injection тестове (ранна, средна, късна грешка в ефектите) доказват три неща: недовършеното плащане е изключено от потребителите, операторът го вижда, няма второ плащане.
- Инструментът за довършване/съгласуване остава дълг.
