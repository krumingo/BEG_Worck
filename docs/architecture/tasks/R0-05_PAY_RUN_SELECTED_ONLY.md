## Какво е сега (проверено в main)

- `backend/app/routes/pay_runs.py`, `create_pay_run` (≈ред 543): `preview = generate_pay_run(...)` връща **всички** служители с одобрени отчети; `override_map` пази само изпратените редове.
- Цикълът `for row in preview["rows"]:` (≈ред 569) обхожда **всеки** служител от прегледа, не `data.rows`. Служител, който не е в избора, получава ред в Pay Run-а.
- `paid_now = ... if ovr else row["remaining_after_payment"]` (≈ред 585): за неизбран служител `paid_now` е **целият остатък**. Значи му се правят фиш, разпределения и (при mark-paid) изходящо плащане.
- `update_pay_run` (PATCH, ≈редове 1085, 1096) има същия дефект.
- `selected_report_ids` се записва, но не ограничава `earned`.

## Обхват

1. **Само избраните:** `create_pay_run` и `update_pay_run` обработват само служителите от `data.rows`. Служител от `data.rows`, който не е в прегледа за периода → `400`. Празен `data.rows` → `400` (не „всички“).
2. **`paid_now` по подразбиране:** когато за избран служител не е зададена сума, подразбиращата се стойност е **0**, не „целият остатък“. Ако фронтендът разчита на старото поведение (изпраща ред без сума и очаква остатъка), Code проверява `frontend/src` и описва решението в PR — не се променя UI без да е нужно; ако е нужна промяна в UI, тя е минималната, и се описва.
3. **`selected_report_ids`:** когато са подадени, `earned` се смята само от тези отчети; ID, което не принадлежи на служителя или на фирмата → `400`.
4. **Съществуващи Pay Run-ове не се пипат.** Без миграция и без поправка на данни. Какво вече е създадено погрешно се установява от отчета за изложеност (стъпка R0-08), не от тази задача.
5. Проверка, че `generate_pay_run` (прегледът) е непроменен: той продължава да показва всички служители, защото е преглед. Дефектът е в създаването.

## Тест на живо с бот (задължителен)

- Локално копие: MongoDB в Docker, backend, frontend build. Само тестови данни.
- Една фирма с трима служители и одобрени дневни отчети за седмицата; един Admin.
- Playwright бот:
  1. Влиза като Admin → отваря страницата Pay Run → скрийншот: прегледът показва тримата.
  2. Избира **само един** → потвърждава → скрийншот на резултата: само един служител във Pay Run-а, един фиш.
  3. Проверка през API на създадения Pay Run: един ред. Скрийншот или запис на отговора.
- Скрийншотите в `docs/evidence/R0-05/`, изброени в PR-а. Ако UI не позволява да се избере само един служител, това се описва като отделна находка, не се заобикаля.
