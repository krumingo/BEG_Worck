# R0-06 — платен Pay Run не се отваря и не се плаща втори път (AUD-043)

> Статус: **ПРЕДЛОЖЕНА — чака „да“ от Крум**

## Какво е сега (проверено в main @ 078b8e7, `backend/app/routes/pay_runs.py`)

1. **`mark_pay_run_paid`** (≈ред 1153): проверката `if run.get("status") == "paid"` и записът `update_one({"id": run_id}, {"$set": {"status": "paid", ...}})` са две отделни стъпки. Две едновременни заявки минават и двете през проверката → **двойно плащане**: по един `finance_payments` Outflow на служител на заявка, двойно намаляване на аванси (`advances.remaining_amount`), двойно `sync_on_paid`. Няма idempotency ключ. Статус `cancelled` също не се отказва.
2. **`reopen_pay_run`** (≈ред 1402): отказва само `cancelled`. Пуска **платен** Pay Run: статус → `reopened` (или само редове), фишовете стават `superseded`. **Парите, вече излезли от Каса/Банка** (`finance_payments`), и намалените аванси **остават**. Следва PATCH (промяна) и нов `mark-paid` → втори изходящ запис за същите служители = **двойно плащане**.
3. Няма път за корекция на платен Pay Run: по CLAUDE.md §7 коригирането е reversal/correction, не директна редакция. Reversal + Approval още не съществуват (W0-07), затова тук се **блокира**, не се имитира.

## Обхват

1. **`mark-paid` — атомарно и идемпотентно.**
   - Преходът към `paid` е един атомарен условен запис (`find_one_and_update` / `update_one` с филтър на разрешен статус, напр. `status: {"$in": ["draft", "confirmed", "reopened"]}` — Code потвърждава точния списък по модела и по това, което UI реално прави: „Потвърди плащане“ вика create → mark-paid) и проверка на резултата. Който не спечели прехода → `409`/`400` „Already paid“ без никакъв страничен ефект.
   - Всички странични ефекти (фишове, аванси, `finance_payments`, `sync_on_paid`) се изпълняват само от заявката, спечелила прехода. Втора едновременна заявка не създава `finance_payments`, не намалява аванси.
   - `cancelled` → отказ.
   - Ако има Mongo транзакция в тенант слоя (`TenantData`), да се ползва за целия блок; ако няма — Code описва как се гарантира, че при грешка по средата не остава `paid` без плащания (или обратното) и каква е стратегията за повторен опит. Решението се описва в PR-а.
2. **`reopen` — платен Pay Run не се отваря.**
   - Run със статус `paid` → `409` с ясно съобщение. Същото за reopen на редове (`employee_ids`) на платен run и за всеки ред с `row_status`/плащане, което вече е платено.
   - Неплатени (`draft`, `confirmed`) и вече `reopened` остават както досега.
   - Нищо не се записва при отказ (побайтово еднакво състояние).
3. **PATCH върху платен run** → отказ (провери дали вече е така след R0-05; ако не — отказ), със същите гаранции.
4. **Корекция на платен run** — извън обхват. Записва се като дълг: „reversal + Approval (W0-07/FLOW-033)“. Съобщението на отказа сочи към това („платен Pay Run се коригира с reversal, не с отваряне“).
