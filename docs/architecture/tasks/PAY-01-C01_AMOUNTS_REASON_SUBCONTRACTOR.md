# PAY-01-C01 — сума и причина в плащанията; сторно на плащане към подизпълнител
> ОДОБРЕНА — прилагане на канона, без ново бизнес решение: CLAUDE.md §14 (validation/DQ), FLOW-006, Р23. PR #70 @ a0dec8b. Codex: да.

## Част 1 — сега (одит #70)
- **PAY-N1 (HIGH, дълг от main):** `POST` плащане, трансфер и allocate в `finance.py` приемат `amount` = nan/inf/1e309 → записват ред и после 500. Сумата трябва да е крайно число > 0, иначе 422 и **нищо записано**. Същото правило като SEC-01-C03 (#69) — ако имате общ helper, сложете го в отделен модул без конфликт (напр. `app/services/money_amount.py`); SEC-01-C03 прави същото за своите пътища, сливането се урежда при merge.
- **PAY-N2 (LOW):** причината за сторно/отмяна — максимум 500 знака, без контролни знаци (NUL, ESC, bidi, zero-width); иначе 400.
- Тестове: nan/inf/-inf/1e309/""/-1/0 → 422, 0 реда, за create/transfer/allocate; причина — дълга, с контролни знаци → 400; трите режима.

## Допълнение A (06.11) — FLOW Guard FG-45
- Сторно на плащане, което идва от друг модул (Pay Run/заплата, аванс/заем/погасяване от hr, плащане към подизпълнител), без обновяване на модула създава разминаване между регистрите (FLOW-006). Докато модулът няма свое сторно: **409 SOURCE_MODULE_REVERSAL_REQUIRED**, нищо записано. Произходът — по полетата, които тези модули записват (категория/source/reference); опиши ги в HANDOFF. Подизпълнителите: 409 сега; Част 2 (след #69) го заменя с истинско сторно в модула.
- Тестове: плащане от pay run / аванс / подизпълнител → 409, 0 реда; ръчно плащане → сторно както досега.

## Допълнение B (06.11) — Р29
- Money POST/DELETE в `finance.py` (плащане, трансфер, account-funding, other-expense/income, quick-pay, allocate, сторно, отмяна) без `Idempotency-Key` → отказ `IDEMPOTENCY_KEY_REQUIRED`, нищо записано. Където още няма idempotency — добави по W0-04 механизма. Фронтендът праща ключ навсякъде (провери). Тестове: без ключ → отказ; повтор със същия ключ → същият отговор, 1 ред.

## Допълнение C (06.11) — одит D5-R1/R2 (HIGH, дълг от main)
- Едновременни allocate с различни ключове надвишават сумите (160 на плащане 100; 1600 на фактура 1200 — 5/5). FLOW-006/CLAUDE §14: разпределението не може да надвиши наличното. Проверката „налично“ и записът да са атомарни спрямо плащането **и** фактурата (заключване на реда на плащането както в C01A-1 + на фактурата, или условен update върху агрегат). Тест: 6 паралелни allocate → сумата никога не надвишава; отказаните — 409, нищо записано.
- IDEM-IDX-1 (липсващ индекс) се оправя отделно в W0-04-C01 от main; не го дублирай тук — в тестовете си създавай индекса както bootstrap-а.
