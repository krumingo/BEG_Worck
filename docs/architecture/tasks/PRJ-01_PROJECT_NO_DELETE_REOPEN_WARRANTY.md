## 1. FG-239 (high) — без hard delete на обект
`DELETE /projects/{id}` (projects.py:321-339) изтрива обект с историята. Замени с архивиране/анулиране (статус, причина, AuditEvent; Owner/Admin); обект с каквато и да е бизнес връзка (оферти, актове, фактури, плащания, склад, отчети, файлове) никога не се изтрива; DELETE → 409 с указание. Тест за всяка връзка.

## 2. FG-237 (high) — повторно отваряне Completed → Active (FLOW-001 P-08)
Днес Completed блокира всеки запис и няма път обратно. Добави контролиран преход Completed → Active с причина, AuditEvent и права по канона (провери FLOW-001 за изискваното одобрение; ако е мълчалив — Owner, дълг). Тест.

## 3. FG-238 (medium) — снимки/доказателства
Снимка на обект (evidence) се изтрива заедно с файла (projects.py:957-978). Без hard delete: скриване/архив с причина + AuditEvent; оригиналният файл в customer storage не се трие (CLAUDE.md §4, File Registry). Тест.

## 4. FG-236 (high) + Р54(1) — гаранция
Тип „Warranty“ не се сменя след първия запис (PUT → 409). Миграция (dry-run → одобрение → --apply, идемпотентна, AuditEvent): всеки съществуващ Warranty проект получава връзка `warranty_of_project_id` към оригиналния обект (ако не може да се определи — DQ задача, без да се измисля); нов път за гаранционна работа към оригиналния обект. Без изтриване на стари проекти.

## 5. FG-240 + Р54(2) — оценка на подизпълнител
`subcontractor_performance`: запис само SiteManager (технически ръководител), Owner, Admin; версия + AuditEvent; Viewer и др. → 403. `actual_paid_amount` не се приема от заявка — изчислява се от Payment ledger (FLOW-006) при четене; съществуващите ръчни стойности остават в историята, но не се ползват. Тест.
