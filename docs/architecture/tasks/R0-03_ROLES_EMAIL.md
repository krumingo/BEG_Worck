Сценарий от одита: Счетоводител сменя ролята си на Admin през `/employees/.../basic` → като Admin сменя паролата на Owner → поема фирмата.

## Обхват

### А. Роли — без ескалация
Йерархия: `Owner` > `Admin` > всички останали.
1. `/employees/{id}/basic` престава да приема `role` и `email`. Ако ги има в заявката → **400** (не тихо игнориране), нищо не се пише. Името, телефонът и аватарът остават, както досега.
2. Смяна на роля се прави само през `PUT /users/{id}` и само от Admin/Owner:
   - никой не сменя **собствената** си роля → 403;
   - никой не дава роля **над своята** (Admin не дава `Owner`) → 403;
   - само Owner променя Owner: роля, `is_active`, парола (`/admin/set-password`), изтриване → иначе 403;
   - последният активен Owner на фирмата не може да бъде понижен, деактивиран или изтрит → 409.
3. Approval: смяна, засягаща Owner, по канон изисква Approval (§8). Canonical DQ/Approval runtime още не е готов (W0). В R0-03 правилото е „само Owner“; **Approval се записва като дълг**, без нов паралелен approval механизъм.
4. AuditEvent при всяка смяна на роля, `is_active`, имейл и admin парола: кой, на кого, преди/след (без пароли/хешове).
5. В `enforce` режим поведението трябва да е същото. Ако RoleAssignment/Permission Service вече пазят нещо от това, Code го използва и описва; не се създава втори източник на роли.

### Б. Имейл — един имейл = един User (Р6)
1. Нормализиране: `strip().lower()` при създаване, при login и при всяка проверка.
2. Създаване на User (всички пътища: `auth.py` off/shadow и enforce, `platform.py`, onboarding) отказва имейл, който вече съществува **в цялата инсталация** → **409** `EMAIL_EXISTS`. Code описва къде е глобалният регистър на User в `off`/`shadow` и в `enforce` (глобален `db.users` срещу tenant бази) и проверява точно там.
3. Login: ако за един имейл има повече от един User → **не** влиза случаен. Отговор **409** `DUPLICATE_IDENTITY` с общо съобщение (без да издава фирми) + AuditEvent. Един User → както досега.
4. Смяна на имейл не е в обхвата (няма такъв маршрут след т. А1). Ако Code намери друг път за смяна на имейл, описва го и прилага същата проверка.
5. **Съществуващи дубликати — без миграция.** Нов read-only скрипт `scripts/r0_03_email_duplicates_report.py`: брои User по нормализиран имейл и печата само брой и маскирани имейли (`iv***@abv.bg`) + id-та. Нищо не пише.
6. Уникален индекс: **не** се създава автоматично в този PR. Пакетът подготвя функцията за индекса (по нормализирано поле или `collation`, Code обосновава), но пускането ѝ е отделна стъпка след отчета за дубликати и „да“ от Крум (R0-09 данни). Записва се като дълг.

## Забранено
- Миграции, промяна на данни, автоматично сливане на дубликати, production, merge, deploy.
- Нов модел TenantMembership/User — това е AUTH-01 (R0-04, PR #56). Тук само проверките.
- Промени в UI, освен ако бот тестът покаже, че екранът за служител праща `role`/`email` към `/basic` и вече чупи — тогава минимална поправка да не ги праща, описана.
- Секрети/пароли в логове, AuditEvent, тестове на живо.

## Тест на живо с бот (задължителен)
Локален backend + frontend, MongoDB в Docker, фирма с Owner, Admin, Accountant:
1. Ботът влиза като Accountant, отваря картата на служител и опитва смяна на роля (UI или заявка от сесията) → отказ; скрийншот на непроменената роля.
2. Като Admin опитва смяна на паролата на Owner → отказ (скрийншот).
3. Като Owner сменя ролята на Admin → успех (скрийншот).
4. Опит за нов User с имейл от друга фирма → 409 (скрийншот/JSON).

Скрийншоти и JSON в `docs/evidence/R0-03/`.
