## Monitoring and scheduler

- A tenant-resolved, provider-neutral runner selects bounded pages of registered current file/version/location originals using risk/document type/`last_verified_at` inputs already present in FLOW-016. The concrete production cadence, policy values and cron deployment are **not** defined here: they are configurable/TBD and default to no automatic production activation. A test/manual trigger may execute the runner with explicit configuration.
- Each check invokes the existing `FileIntegrityService.check()` with an explicit tenant-scoped, FLOW-002-authorized service principal; no unrestricted system bypass or new implicit role grant. Missing service authorization fails closed before provider access. Reuse the W0-06B provider bindings/credentials contract; no automatic activation or binding change.
- Bound every run by configured batch size and continuation cursor, with durable per-tenant run ID, last/next due metadata, result counts and item checkpoints. A retry resumes without silently skipping a file or duplicating its finding/alarm/audit effect. Provider errors are bounded by retry/backoff and do not create unbounded loops or hold a global tenant lock indefinitely. No hard-coded business SLA is inferred from a retry interval.
- A database-enforced tenant-scoped lease/fencing or equivalent atomic claim prevents duplicate concurrent workers, including across processes. A crashed worker can safely resume after its claim expires; a stale worker cannot commit after a newer owner takes over. The implementation must prove duplicate-run and crash/restart behaviour on disposable real MongoDB, not only a fake.
- Keep `provider_unavailable` and `permission_failure` distinct from `missing_original`, `checksum_mismatch` and `external_change`. A transient outage remains an outage, never evidence of absent/corrupt bytes. Persistent-vs-transient classification may use an explicitly supplied policy; without an approved threshold, do not invent one or silently close an unresolved integrity finding.

## Finding and technical alarm lifecycle

- Persist one open finding per tenant + file + version + location + finding type (or a stricter deterministic identity that also handles provider migration). Repeated checks update `last_seen` and evidence/history, not duplicate open alarms. Track `first_seen`, `last_seen`, `resolved_at`, `reopened_at` and append-only open/observed/resolved/reopened transitions with idempotent event keys.
- Each finding/alarm exposes tenant, provider binding/kind, `file_id`, version, location, finding type, expected/observed evidence, affected-record count and grouped affected records, W0-06B severity, and an alarm level capable of `informational`, `warning`, `critical`. A deterministic normalization of the existing W0-06B severity may be used; do not invent recipient, deadline or business escalation SLA. Preserve the original severity alongside the normalized level.
- Resolve affected records only through W0-06B `AffectedRecordResolver`/active `FileRelation` in the same tenant; include its canonical groups (projects; offers/contracts/annexes; acts/invoices; deliveries; daily reports; tasks; defects/warranties; assets/repairs; other). Refresh counts/links when relations change. Dangling targets remain explicit. Any read/API projection, if added, must enforce FLOW-002 and tenant/project/module/sensitivity scope; never expose another tenant's record labels or provider identifiers.
- A successful provider response alone does **not** resolve a missing/checksum/permission/external-change finding. Resolution requires a new type-specific verification against the canonical expected location, bytes/checksum, provider identity/version and access proof: missing → original exists and is identified; checksum mismatch → canonical expected checksum and size match; permission failure → actual authorized read succeeds; provider unavailable → provider verification succeeds; external change → explicit re-verification/decision under the existing W0-06B contract, never silent adoption as a new FileVersion. A finding may reopen after a later failure with its history preserved. If proof is incomplete, leave it open.
- AuditEvent is the single FLOW-040 trail for checks and lifecycle transitions, with correlation/idempotency and sanitized evidence references. No raw credential, token, signed URL, document bytes or sensitive provider error text in findings, events or logs. No permanent public URL or preview/cache substitution for an original.
