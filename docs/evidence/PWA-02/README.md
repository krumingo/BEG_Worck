# PWA-02 — офлайн опашка и синхронизация: HANDOFF

Задача: `docs/architecture/tasks/PWA-02_OFFLINE_QUEUE_SYNC.md` + правила Р61 (клон `claude/happy-meitner-bmcnel`).
Решения: Р82 (Крум, 09.11.2026 — обхват, денят по София, еднакво отбелязване = без дубликат) и отговорите
на оркестратора Q1–Q6 (FLOW Guard оракул Q011). База: main `3863610`. Карта на релациите: `DESIGN.md`.

**Всичко е зад feature flag `offline_queue`, по подразбиране ИЗКЛЮЧЕН.** Сървърът чете флага при всяка
заявка; включване/изключване записва AuditEvent (`sync.flag_set`). Без флага: всички `/api/sync/*` за
теренни потребители → 403 `OFFLINE_QUEUE_DISABLED`, екраните работят както преди (само онлайн).

**Не се обявява MFE приемане / Implementation Gate PASS** (Q1). Това е първата офлайн стъпка.

## Засегнати FLOW-ове и source of truth
- FLOW-037 (Modern Field Experience — офлайн, статуси §9) — думите на статусите са дословно оттам.
- FLOW-013/014 (присъствие, дневен отчет на техника) — офлайн записът минава през **същия домейн
  сервиз** като онлайн endpoint-а (`create_attendance_entry`, `submit_daily_report`). Няма втори запис.
- File Registry (CLAUDE.md §2.6) — още го няма → снимката спира на „Чака качване на файл“, оригиналът
  остава криптиран на телефона.
- Source of truth остава домейн колекцията. `sync_*` колекциите са разписки/опашки за решения, не
  втори регистър (CLAUDE.md §2.12).

## Какво прави
| Тип (само тези 3, Q1) | Офлайн | При синхронизация |
|---|---|---|
| Присъствие (самоотбелязване) | криптирано на телефона | същият сервиз; ден = локалният ден на фирмата (Europe/Sofia) към момента на записа |
| Дневен отчет на техника (пълен) | криптирано на телефона | `submit_daily_report`; затворен ден (одобрен/платен) → конфликт |
| Снимка от обекта | оригиналът криптиран на телефона, SHA-256 изчислен там | „Чака качване на файл“ (няма File Registry) |

Всичко друго (плащания, фактури, актове, договори, одобрения, IBAN, роли, …) → „Това изисква интернет“ (Р61-1).

- **Идемпотентност:** `sync_receipts` уникален по (org, user, idempotency_key) + отпечатък. Повторно
  изпращане → същият резултат (`replay: true`), без дубликат. Еднакво самоотбелязване след офисното
  (същия ден, обект, статус) → „Синхронизирано“ без нов запис (Q3).
- **Конфликт (видим, никога автоматично сливане):** различна стойност, `version` ≠ `base_version`,
  одобрен/платен/затворен ден. Конзолата показва диф „Офис / Телефон“. Одобрен/платен → само
  корекция/сторно (409 `CORRECTION_OR_REVERSAL_REQUIRED`), Q4.
- **Закъснял запис** (ден преди днешния по София или часовник > 10 мин разлика) → `sync_late`
  „Закъснял — чака офиса“. Собственик/Админ: потвърди / коригирай / откажи, с причина + AuditEvent;
  реалната дата на въвеждане се пази; датата на записа се приема **само** при потвърждение (Q2).
  Работникът вижда решението на телефона (разписките се опресняват).
- **Устройства:** регистрират се при вход. Блокирането спира устройството, не потребителя (Q6).
  Блокирано устройство → 403 `DEVICE_REVOKED` + карантина; телефонът изтрива опашката, ключовете и
  device id и показва „Устройството е блокирано“. Изход без блокиране **не** трие неизпратените
  (предупреждение при изход, Р61-5).
- **Сигурност на телефона:** AES-GCM 256, неекспортируем ключ за всеки tenant+потребител,
  собственикът е вързан като AAD; в IndexedDB открити са само полетата за маршрутизиране.
- **Версия:** явно поле `version` + CAS върху засегнатите записи (добавъчно; липсващо = 0).
- Всеки запис/решение → canonical AuditEvent (`source_flow FLOW-037`, `source_channel offline_sync`).

## AUDIT-2 (PR #92 на 614510e) — поправено
- **PWA92-M1 (блокиращо) — дневен отчет два пъти при срив/повторение.** Преди: черновите се вмъкваха
  и чак след това се маркираха със `sync_local_id` (две неатомарни стъпки). Сега
  `submit_daily_report_core(..., sync_stamp=…)` (добавъчен параметър; онлайн route-ът е същият и
  работи както преди — без транзакция, без нови полета) вмъква всяка чернова **вече маркирана**
  (`sync_local_id` + `sync_entry_index`) и всички записи на отчета вървят в **една транзакция**.
  Предпазител: уникален частичен индекс `(org_id, sync_local_id, sync_entry_index)` върху
  `employee_daily_reports` (само редове от офлайн пътя); при take-over handler-ът първо търси
  вече записаното, а `DuplicateKeyError` се връща като „вече записано“.
  Тестове (реален Mongo): срив между черновите и края на записа → 0 реда, разписка `retry` →
  повторение → точно 2 реда (2 записа в отчета) → пак → `replay`, 2 реда; записът е минал, заявката е
  умряла преди разписката, stale take-over след 3 мин → `already`, пак 2 реда; втори ред за същия
  запис → `DuplicateKeyError`; онлайн отчетът — 200, същият отговор, без sync полета.
  Червено на 614510e: harness-ът пада на първата стъпка (сривът дава 500 за целия пакет).
- **PWA92-N1 — неочаквана грешка в един запис.** `process_item` хваща всяка грешка за записа:
  статус `retry`, код `SERVER_ERROR_RETRY`, без вътрешни детайли; останалите записи в пакета
  продължават; пакетът никога не връща 500. Разписка `retry` се поема веднага при следващото
  изпращане; телефонът пази записа („Чака синхронизация“) и опитва пак с backoff (тест в jest).
- **„deciding“ без край.** Решение, прекъснато по средата, се поема след същия прозорец (2 мин;
  ред без печат — веднага), CAS върху `deciding_at`, AuditEvent `sync.decision_taken_over`;
  всяка неочаквана грешка при решение връща записа в „open“.

## Дългове и отворени точки (не са решавани — за Крум / следваща задача)
- **D1 — migration runner** няма в main; индексите се създават идемпотентно при старт/onboarding.
- **D2 — Background Sync без отворена страница:** ключът е неекспортируем и е при страницата; service
  worker-ът само моли отворена страница да изпрати.
- **D3 — карантина без действия:** записите от блокирано устройство само се показват.
- **D4 — флагът се включва само от платформения администратор** (`PUT /api/sync/flag`).
- **D5 — „Кой одобрява ново устройство“** — отворено решение за Крум (Q6). Сега: регистрация при вход.
- **D6 — „Закъснял“ при присъствие:** `create_attendance_entry` сравнява крайния час със
  сървърното време при синхронизация. В пробега офлайн „Присъствал“ след крайния час се записа като
  „Late“ и последващото еднакво „Present“ от телефона отиде в конзолата като конфликт (правилно по
  Q3, но въпросът „кой час важи — на записа или на синхронизацията“ е за Крум).
- **D7 — онлайн endpoint-ът за присъствие ползва UTC ден** (`today_str`), офлайн пътят — ден по
  София. Не е пипнат (съществуващо поведение).
- **D8 — онлайн дневният отчет приема дата от клиента** (FLOW-014 без задна дата) — съществуващо.
- **D9 — затворено с FG-626:** всички writer-и на присъствие/дневен отчет вдигат `version`; applier-ът
  сравнява и целия видян запис.
- **D10 — изгубен отговор онлайн → записът отива в опашката:** при присъствие повторението е
  „Синхронизирано“ (еднакво); при дневен отчет е възможна втора чернова. Остатъчен риск.
- **D11 — срив между домейн записа и разписката:** смекчено с проверка по `sync_local_id`;
  остатъчен риск за дневния отчет.

  показват. Съществуваща аномалия, не е поправяна (CLAUDE.md §18). PWA-02 показва статусите в
  собствени елементи и не разчита на toast.
- **D13 — задачи, отговорно пазене (custody) и останалите видове** — по-късно (Q1, Q5).
- **D15 — индекси за нова база при onboarding:** днес onboarding записва новата фирма в същата
  оперативна база (`database_name = op_db.name`), която стартът вече индексира
  (`ensure_sync_indexes_for_installation`). Когато onboarding започне да създава отделна база, там
