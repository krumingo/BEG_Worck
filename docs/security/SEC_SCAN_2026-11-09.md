## Кратко резюме (за Крум)

**Няма открит злонамерен, скрит или „задна врата“ код** в нашия backend и frontend. В историята на Git също **няма изтекли реални пароли или ключове**. Има само тестови и измислени пароли и публичния PostHog ключ.

Има обаче **два сериозни остатъка от Emergent**, които трябва да махнем преди реална работа с клиенти:

1. **Чужд скрипт от Emergent се зарежда на всяка страница.** Това е `emergent-main.js`, включително в продукционния build. Той работи със същите права като нашето приложение. Затова технически може да прочете входния токен (`bw_token`) на всеки потребител. Не успях да прочета съдържанието му, защото мрежата на тази сесия блокира `assets.emergent.sh`. Това **не доказва**, че скриптът е злонамерен. Но той е код, който не контролираме и който Emergent може да смени по всяко време. **Препоръка: да се махне.**
2. **PostHog (аналитика) на main още е старата версия на Emergent.** Тя е с вграден ключ и с включен запис на сесии. Данните от екрана може да отиват в PostHog акаунт, за който не е ясно чий е. PR #88 вече поправя това. Трябва да се merge-не и да се провери чий е ключът.

Средни неща за оправяне:

- ако в сървъра липсва настройката `JWT_SECRET`, кодът не спира, а продължава с известна парола;
- AI функциите изпращат снимки и текстове през услугата на Emergent;
- един служебен адрес (`/api/internal/run-reminder-jobs`) може да се извика без вход;
- приложението може да бъде вградено в чужд сайт;
- печатът на фишове не „почиства“ имената на служителите.

Нищо от това не изглежда умишлено вредно. Това са стандартни остатъци от шаблона на Emergent и обикновени технически дългове.

## High

### H-1 — Unreviewed third-party script `emergent-main.js` runs on every page, in production, on the token's origin
- **Where:** `frontend/public/index.html:26` `<script src="https://assets.emergent.sh/scripts/emergent-main.js"></script>`. The script is synchronous, has no `integrity`/SRI, and has no version pin.
- **Evidence:** `ops/synology/deploy/Dockerfile.frontend` runs `yarn build` on this `public/index.html`. The production bundle therefore ships the tag. The session token is kept at `localStorage["bw_token"]` (`frontend/src/contexts/AuthContext.js:16,44`, `frontend/src/lib/api.js:9`). The platform token is kept at `localStorage["bw_platform_token"]` (`AuthContext.js:90,131`).
- **What the script does: NOT VERIFIED.** The fetch was blocked by this session's network policy: `curl` got `CONNECT tunnel failed, response 403` and WebFetch got `ENOTFOUND assets.emergent.sh`. A fetch through an archive mirror was refused by the session's safety policy, and I did not work around it. I am **not** claiming anything about its content.
- **Why it matters:** any script loaded this way has full access to the page. It can read `localStorage` (both tokens), read the DOM and form fields, call our API with the user's token, and send data anywhere. Whoever controls `assets.emergent.sh` can therefore take over every user session at any time, now or later, with no change in our repo. This is the "hidden code later" risk in its purest form. No CSP limits it (see M-4).
- **Fix:** delete line 26, and the `DataCloneError` suppressor on line 25, which exists only for that script. If Visual Edits are ever wanted again, inject them only in the Emergent preview, never in the committed template. Then add a CSP `script-src 'self'` (M-4).

### H-2 — PostHog snippet on `main`: hard-coded key, remote loader, session-recording config
- **Where:** `frontend/public/index.html:89-178`. The `posthog.init("phc_…CMjs", { api_host: "https://us.i.posthog.com", person_profiles: "identified_only", session_recording: { recordCrossOriginIframes: true, … } })` call is at line 171.
- **Evidence:** the stub injects `https://us-assets.i.posthog.com/static/array.js` at runtime, which is remote, unpinned code with no SRI. The key has been in the file since the very first commit `9cdff159` (2026-05-08, `emergent-agent-e1`). It is part of Emergent's template, so **the PostHog project it reports to may belong to Emergent, not to BEG_Work**. That cannot be determined from the repo.
- **Why it matters:** every page view, plus any session replay the remote project enables, goes to a third-party analytics project. A replay can show financial screens and names. Replay is controlled by the *remote project settings*, not by our code. The loaded `array.js` is also same-origin code (same risk class as H-1, from a smaller vendor surface).
- **State:** PR #88 (commits `01f90296` R68 and `30206f63` PWA88-N1) replaces this with bundled `posthog-js` 1.200.0. That version is anonymous-only, has no recording, has no hard-coded key, and needs no external script. **This is not yet on `main`.**
- **Fix:**
  - Merge PR #88 (Krum's decision).
  - Confirm in PostHog which account owns the `…CMjs` key. If it is not Krum's, ask Emergent to delete the data, or at least stop using that key.
  - Supply-chain check for #88, based on my offline knowledge (it may be incomplete): the npm "Shai-Hulud 2.0" worm (Nov 2025) published malicious `posthog-js` / `posthog-node` versions, for example `posthog-js@1.297.3`. `1.200.0` predates that. Make sure `yarn.lock` resolves exactly `1.200.0` with its `integrity` hash, and keep `--frozen-lockfile`.

## Medium

### M-1 — Live JWT verifier fails open to a known secret
- **Where:** `backend/app/deps/auth.py:20` `JWT_SECRET = os.environ.get('JWT_SECRET', 'dev-secret-key')`. This module is the one actually used: `create_token` is at line 33 and `get_current_user` at line 44, and `server.py:55-60` re-exports it.
- **Evidence:** the stricter `backend/app/utils/crypto.py:11-21` (it exits when `ENV=production`) is **not** the verifier used by routes.
- **Why it matters:** if `.env` ever lacks `JWT_SECRET`, the app starts normally and anyone can forge a token for any `user_id`/`org_id`, Admin included. They need only the public string `dev-secret-key` and a known user id.
- **Mitigation already present:** the Synology release layout requires the key (`ops/release/synology/layout.json:22` `required_env_keys … "JWT_SECRET"`), and `backend/scripts/smoke_test.py:28` checks it.
- **Fix:** make `deps/auth.py` import from `utils/crypto.py`, or fail closed the same way. Refuse to start outside an explicit dev/test env if the secret is missing or shorter than 32 chars.

### M-2 — AI features send tenant data through Emergent's LLM proxy; the package is unpinned and not in requirements
- **Where:**
  - `backend/app/services/ai_proposal.py:247-265`
  - `backend/app/routes/assets_ai_intake.py:69-84` (images)
  - `backend/app/routes/assets_batch_intake.py:117-128` (images)
  - `backend/app/routes/smr_analysis.py:1025-1027`
- **Evidence:** each of these does `from emergentintegrations.llm.chat import …` with `EMERGENT_LLM_KEY`. `emergentintegrations` is **not** in `backend/requirements.txt`. It comes from Emergent's private package index, so it is unpinned, has no hash, and could not be reviewed here.
- **Why it matters:**
  - Photos, SMR texts and offers go to Emergent's servers, which then forward them to OpenAI/Anthropic. That is a third-party data processor outside the canonical AI rules (CLAUDE.md §10).
  - Whatever code that package contains runs inside the backend with DB access.
  - On the Synology image the import fails, so these endpoints return 500s. That is a functional issue rather than a security one.
- **Fix:** replace it with a direct, pinned provider SDK behind an adapter, with a tenant-owned key. Until then, do not set `EMERGENT_LLM_KEY` in production.

### M-3 — Unauthenticated cross-tenant job trigger
- **Where:** `backend/app/routes/attendance.py:897-900`. `POST /api/internal/run-reminder-jobs` has no `Depends`.
- **Why it matters:** anyone on the internet can repeatedly start `run_reminder_jobs()` (`attendance.py:310`). It walks every tenant and writes reminder logs and notifications. The result is resource drain and possible notification spam. The in-process loop (`server.py:582-590`) already runs the job every 15 minutes, so the HTTP route is not needed.
- **Fix:** remove the route, or require `require_platform_admin`.

### M-4 — No CSP / framing protection, so a framing site can make the page load *more* Emergent code
- **Where:** `nginx.conf` (whole file) has no `Content-Security-Policy`, `X-Frame-Options`/`frame-ancestors`, HSTS or `X-Content-Type-Options`. `frontend/public/index.html:30-49` loads `debug-monitor.js` (also unreviewed, same fetch failure) and `https://cdn.tailwindcss.com` whenever `window.self !== window.top`.
- **Why it matters:** any website can iframe the app and trigger those extra scripts in our origin. Combined with H-1/H-2 there is no second line of defence. Framing also enables clickjacking.
- **Fix:** remove lines 30-49, then add `Content-Security-Policy: default-src 'self'; script-src 'self'; frame-ancestors 'none'; …`, `X-Frame-Options: DENY` and `X-Content-Type-Options: nosniff`.

### M-5 — Stored XSS in same-origin print windows
- **Where:**
  - `frontend/src/components/PayRunPrintView.js:16,56,94,117`, which writes `first_name`, `last_name` and `run.number` into `w.document.write(...)` unescaped;
  - `frontend/src/components/UnitQrBlock.js:33`, which does the same with `qrId` and `serialNo`.
- **Why it matters:** a window opened with `window.open("")` is same-origin. A name such as `<img src=x onerror=…>` runs script that can read `localStorage.bw_token` of whoever prints the payslip, typically an Admin or Accountant. This is an insider/privilege-escalation path, not an external one.
- **Fix:** HTML-escape every interpolated value, or build the print view with React/DOM APIs.

## Low

### L-1 — CORS defaults to `*` with credentials
`backend/server.py:379-385` uses `allow_origins=os.environ.get('CORS_ORIGINS', '*')` with `allow_credentials=True`. Auth is a Bearer header, not a cookie, so the practical impact is small. The release layout requires `CORS_ORIGINS` (`layout.json:22`). Fix: no default. Refuse to start if the variable is unset in production.

### L-2 — `/api/media/avatar/{filename}` serves any file in `uploads/` without auth
`backend/app/routes/media.py:211-221` has no auth, and despite its name it is not limited to avatars. Path traversal is blocked. Protection relies on unguessable (UUID) file names. Fix: look up the name in `media_files` and serve it only if the file is a profile image.

### L-3 — Client IP taken from `X-Forwarded-For` unconditionally
`backend/app/routes/platform.py:119-131` (`get_client_ip`) trusts the header. The bootstrap endpoint's "5 per 10 min per IP" limit can be bypassed by rotating the header. Bootstrap is disabled when `PLATFORM_BOOTSTRAP_TOKEN` is unset. Fix: trust the header only from the nginx hop.

### L-4 — Emergent dev-server plugin with a file-write + `git commit` endpoint
`frontend/plugins/visual-edits/dev-server-setup.js:381-470, 898-912` provides `POST /edit-file`:
- It writes source files and runs `execSync("git … add \"${file}\"")`.
- CORS allows `*.emergent.sh`, `*.emergentagent.com` and `*.appspot.com` (lines 348-372).
- Auth is the supervisor password read from `/etc/supervisor/…` (lines ~320-340). If that password is missing, every request is refused with 401.
- It is loaded only by `craco start` (`frontend/craco.config.js` `isDevServer`), never in `yarn build`.

Low risk, but it is dead Emergent tooling with a shell-string `execSync`. Fix: delete `frontend/plugins/visual-edits/` and its wiring in `craco.config.js`. `plugins/health-check/` is opt-in, read-only and harmless.

### L-5 — Outdated or over-broad backend dependencies (offline CVE knowledge, may be incomplete)
`backend/requirements.txt`:
- `starlette==0.37.2` (via fastapi 0.110.1): CVE-2024-47874 (multipart DoS, fixed in 0.40.0) and CVE-2025-54121 (fixed in 0.47.2).
- `pymongo==4.5.0`: CVE-2024-5629 (fixed in 4.6.3).
- `ecdsa==0.19.1`: Minerva timing issue, no upstream fix. It is pulled in by `python-jose`.
- `google-auth==2.49.0.dev0` is pinned to a **pre-release**.
- The file is a full `pip freeze` of Emergent's base image. It carries many packages the app does not import at runtime, which widens the supply-chain surface: `litellm`, `huggingface_hub`, `hf-xet`, `tokenizers`, `tiktoken`, `google-generativeai`, `google-genai`, `openai`, `s5cmd`, `boto3`, `black`, `mypy`, `flake8`, `pytest`, `jq`, `numpy`, `pandas`.
- Every package is exact-pinned (`==`), but there are no hashes (`--require-hashes`).
- Known-malicious check (offline): `litellm` 1.82.7/1.82.8 were compromised on PyPI in 2026. The pinned `1.80.0` is not one of them.

Fix: trim to what is imported, add hashes, and upgrade fastapi/starlette and pymongo.
